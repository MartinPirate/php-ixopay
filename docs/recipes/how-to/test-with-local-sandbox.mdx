# How to test with a local sandbox

Use this recipe to exercise IXOPAY SDK flows against a local sandbox API before testing against a shared or production-like gateway environment.

## Prerequisites

- The IXOPAY PHP SDK installed with Composer.
- A local PHP runtime.
- A merchant integration that can switch gateway URLs outside production.

## Recipe

### Step 1 - Start the local sandbox API

Run the sandbox router from this repository. It exposes transaction, status, redirect, test-credential, test-method, callback, and webhook replay endpoints for predictable scenarios.

```bash
php -S 127.0.0.1:8089 examples/sandbox/router.php
```

### Step 2 - Point the SDK at the sandbox

Use the SDK's configurable API URL in non-production code and send explicit payment-method and scenario headers.

```php
Client::setApiUrl('http://127.0.0.1:8089/');

$client = new Client('sandbox-user', 'sandbox-password', 'sandbox-api-key', 'sandbox-shared-secret');
$client->setCustomRequestHeaders([
    'Authorization' => 'Basic ' . base64_encode('sandbox-user:sandbox-password'),
    'X-Sandbox-Payment-Method' => 'mpesa',
    'X-Sandbox-Scenario' => 'mpesa-pending',
]);
```

### Step 3 - Run a transaction scenario

Run one of the supported scenarios and inspect the redirect URL, status lookup, and callback payload.

```bash
php examples/sandbox/debit.php redirect card
php examples/sandbox/debit.php card-3ds card
php examples/sandbox/debit.php mpesa-success mpesa
php examples/sandbox/debit.php mpesa-pending mpesa
php examples/sandbox/debit.php mpesa-timeout mpesa
php examples/sandbox/debit.php error card
```

## Validation

- Redirect and card-3DS scenarios return a local hosted-payment redirect URL.
- M-Pesa scenarios expose success, pending, and timeout behavior.
- Error scenarios return a parsed SDK error object.
- Status lookup returns a matching merchant transaction ID and sandbox scenario.
- Callback payload endpoints include a signature generated from the sandbox shared secret.
